# Belloga 하네스: 에이전트에게 규칙을 넣되, 앱 안에서만 그리고 강제하지 않게

Belloga는 Claude Code 세션을 여는 데스크톱 앱이고, 세션을 열 때마다 작업 계획 위치와 작성 규칙을 에이전트에게 넣어 줍니다. 이렇게 에이전트 바깥에서 규칙과 맥락을 공급하는 장치를 하네스라고 부릅니다. 하네스를 만들면서 가장 많이 고민한 것은 "무엇을 넣을까"보다 **"어디까지 넣고, 사용자의 것을 어디까지 건드릴까"**였습니다. 이 글은 그 경계를 정한 결정 기록(ADR) 네 건을 정리합니다.

---

## 원칙 1. Belloga 안에서 연 세션에만 넣는다

Claude Code의 훅은 사용자 전역 설정(`~/.claude/settings.json`)에 등록됩니다. 그래서 처음에는 Belloga 밖의 터미널이나 다른 앱에서 켠 세션에도 같은 안내가 들어갔습니다.

문제는 Belloga 밖에서 일하는 사용자는 그 순간 Belloga를 하네스로 쓰고 있지 않다는 점입니다. 자기 하네스를 따로 쓰는 사용자에게 Belloga의 계획 위치를 권하면 두 규칙이 부딪혀, Claude가 매번 어디에 쓸지 묻게 됩니다.

**결정**: 훅은 `BELLOGA_PANE_ID` 환경 변수가 있는 세션에만 안내를 넣습니다. Belloga는 앱 안의 터미널을 열 때 이 값을 늘 넣고, Claude Code와 그 훅은 터미널의 환경을 물려받습니다. 값이 없으면 훅은 아무것도 내보내지 않고 끝납니다.

기준 값을 고를 때도 이유가 있었습니다. 앱의 훅 서버 포트(`BELLOGA_HOOK_PORT`)를 기준으로 쓰면, 훅 서버가 뜨지 못했을 때 앱 안의 터미널인데도 안내가 빠집니다. pane ID는 터미널을 열 때마다 늘 들어가고, 세션 상태 훅도 같은 값을 기준으로 씁니다.

---

## 원칙 2. 사용자의 설정은 앱이 되돌리지 않는다

세션 상태(작업 중, 권한 대기)와 사용량을 보여 주는 훅은 처음에 상태 바의 칩을 눌러야 설치됐습니다. 누르기 전에는 기능이 없는 것처럼 보여서, 앱이 켜질 때 알아서 설치하고 끄는 스위치는 설정 화면에 두기로 했습니다.

알아서 설치하는 순간, 앱이 사용자의 전역 설정 파일을 고치게 됩니다. 그래서 규칙을 붙였습니다.

- 이미 설치돼 있으면 설정 파일을 다시 쓰지 않습니다.
- **앱이 켜질 때는 스위치가 꺼져 있어도 이미 있는 훅을 지우지 않습니다.** 훅을 지우는 것은 사용자가 스위치를 끌 때뿐입니다. 다른 도구나 사용자가 둔 설정을 앱이 켜질 때마다 건드리지 않기 위해서입니다.
- 사용자 자신의 statusLine은 덮어쓰지 않습니다.
- Belloga statusLine을 한 번 심은 뒤 사용자가 직접 지웠으면 다시 심지 않습니다. 심은 적이 있는지는 앱 설정 파일의 표식으로 가립니다. 사용자의 의사를 앱이 되돌리지 않기 위해서입니다.

---

## 원칙 3. 틀과 규칙은 사용자 파일로, 강제하지 않는다

처음에는 계획 문서의 형식(유형별 섹션, R 번호, `Status:` 줄, 체크박스)이 코드에 박혀 있었습니다. 사람마다 쓰는 틀이 다른데 사용자가 바꿀 수 없었고, 형식의 원본도 훅 안내 문장과 앱의 틀 두 곳에 있었습니다.

**결정**: 템플릿의 원본을 `~/.belloga/agents/templates/`의 사용자 파일로 옮겼습니다.

- 앱은 진행률 표시에 필요한 **골격만** 읽습니다. `type:` 줄, R 번호, `Status:` 첫 줄, R 번호를 참조하는 체크박스입니다. 나머지 섹션 구성은 사용자 마음대로입니다.
- 훅은 템플릿 본문을 넣지 않고 폴더 경로와 "골격은 지키라"는 문장만 넣습니다. SessionStart의 `additionalContext`는 1만 자에서 잘리고, 본문을 넣으면 템플릿을 고칠 때마다 토큰이 늘기 때문입니다. 대신 그 폴더에 읽기 권한을 주어 Claude가 쓸 때 직접 읽게 했습니다.
- 앱은 없는 템플릿만 만들고, 있는 파일은 건드리지 않습니다.

사용자의 하네스 폴더(`~/.claude/`)에 직접 쓰는 방법도 있었습니다. 하지만 그러면 앱을 쓰지 않을 때도 사용자의 하네스가 바뀌어 원칙 1과 같은 충돌이 생깁니다. Belloga의 것은 `~/.belloga/` 아래에만 둡니다.

### 규칙은 따로 켜는 훅으로

`~/.belloga/agents/rules/`의 규칙 파일은 규칙 전용 SessionStart 훅이 넣습니다. 규칙을 이을 때 맨 앞에 **"사용자 자신의 지시와 부딪히면 그쪽을 따르라"**는 문장을 붙입니다. 하네스가 사용자를 이기면 안 되기 때문입니다.

훅은 나눠서 각각 켜고 끌 수 있게 했습니다. 처음에는 세션 상태 훅, 계획 훅, 규칙 훅 셋이었고, 뒤에 worktree 훅이 더해져 넷이 되었습니다. 계획 안내와 규칙을 한 훅에 넣으면 스크립트는 줄지만, "계획은 내 하네스를 쓰고 규칙만 Belloga 것을 쓰는" 조합을 막게 됩니다. 기본으로 자동 설치되는 것은 세션 상태 훅뿐이고, 나머지는 사용자가 켤 때만 설치합니다.

### 테스트한 코드가 곧 실행되는 코드가 되게

훅 스크립트는 독립 파일이라 앱의 다른 모듈을 import할 수 없습니다. 규칙을 잇는 로직을 스크립트에 따로 적으면 테스트한 코드와 실행되는 코드가 갈립니다. 그래서 규칙을 잇는 함수를 `src/shared`의 순수 함수로 두고, 스크립트를 쓸 때 그 함수 본문을 `toString()`으로 넣었습니다. 이 함수는 다른 모듈 값을 참조하지 않도록 문장을 인자로 받습니다. 빌드한 앱이 쓴 스크립트를 실행해 결과가 같은 것도 확인했습니다.

---

## 원칙 4. 사용자의 인증 정보는 main 프로세스 밖으로 내지 않는다

상태 바의 Claude 사용량을 원할 때 새로 가져오려고, Claude Code가 저장해 둔 OAuth 토큰으로 사용량 API를 부르기로 했습니다. 앱이 사용자의 인증 정보를 읽게 되는 결정이라 경계를 분명히 했습니다.

- **토큰은 메인 프로세스 밖으로 나가지 않습니다.** 렌더러, 로그, 저장 파일 어디에도 남기지 않습니다. 화면에는 계산된 사용량만 보냅니다.
- 토큰이 없거나 요청이 실패하면 로그 한 줄만 남기고 이전 값을 둡니다. 토큰을 고치거나 갱신하려 들지 않습니다.
- 공개되지 않은 API라 응답 모양이 바뀔 수 있어서, 해석은 함수 한 곳에 모았습니다.

같은 원칙은 뒤에 Belloga 서버의 세션 토큰에도 그대로 이어졌습니다. 세션의 에이전트가 과거 계획을 검색할 때도 스크립트가 서버를 직접 부르지 않고, 앱 main이 토큰을 붙여 대신 부릅니다.

---

## 정리

네 결정은 결국 하나의 질문에 대한 답이었습니다. "남의 도구(Claude Code) 위에 얹히는 앱이, 사용자의 환경을 어디까지 건드려도 되는가."

- 적용 범위: Belloga 안에서 연 세션에만 넣습니다(환경 변수로 판정).
- 소유권: Belloga의 것은 `~/.belloga/`에 두고, 사용자의 설정은 지우거나 되돌리지 않습니다.
- 강제하지 않음: 템플릿은 사용자가 고치고, 앱은 골격만 읽으며, 규칙은 사용자의 지시에 양보합니다.
- 비밀: 인증 정보는 main 프로세스 밖으로 내지 않습니다.
