# Belloga 동기화 (1) 계획 문서 저장 설계: 해시 주소 저장과 철회한 충돌 판본 저장

Belloga는 에이전트 세션에 브랜치별 작업 계획(`requirements.md`, `design.md`, `tasks.md`)을 넣어 주는 데스크톱 앱입니다. 계획 문서는 저장소를 오염시키지 않으려고 저장소 밖(`~/.belloga/plans`)에 둡니다. 그런데 이 선택 때문에 데스크톱과 노트북을 오가면 코드는 git으로 따라오지만 계획은 따라오지 않았습니다.

여러 기기에서 계획을 이어 쓰려면 서버에 저장하고 동기화하는 경로가 필요했습니다. 이 글은 그 저장 방식을 고른 결정 기록(ADR)과, 구현하면서 그 결정의 일부를 뒤집은 과정을 정리합니다. 이 설계를 동시성과 일관성 측면에서 어떻게 구현했는지는 [2편](/blog/2026-10-21-belloga-sync-2-consistency)에서 다룹니다.

---

## 먼저 제약을 적었다

저장 방식은 데이터가 어떻게 쓰이는지에 따라 답이 달라집니다. 그래서 대안을 비교하기 전에 계획 문서의 쓰임새를 먼저 적었습니다.

- **공동 편집이 아닙니다.** 한 사용자가 기기를 바꿔 가며 씁니다. 여러 사람이 같은 문서를 동시에 고치지 않습니다.
- **쓰기의 대부분은 에이전트가 합니다.** 그래서 두 기기에서 같은 순간에 같은 파일을 고칠 확률은 낮습니다.
- **그래도 충돌은 생깁니다.** 오프라인으로 일한 기기가 늦게 올리는 경우, 이미 계획이 있는 두 기기에서 처음 동기화를 켜는 경우입니다. 충돌이 없다고 가정할 수는 없고, 생겼을 때 데이터를 잃지 않아야 합니다.

정리하면 "충돌은 드물지만 0은 아니고, 생기면 잃지 않아야 한다"입니다. 아래 대안은 모두 이 문장에 비춰 판단했습니다.

---

## 검토한 대안 세 가지

| 방식 | 장점 | 기각한 이유 |
| ---- | ---- | ---- |
| DB에 저장마다 전체 텍스트를 새 행으로 쌓기 | 구현이 쉬움 | 체크박스 하나만 바뀌어도 문서 전체가 쌓여 테이블과 백업 비용이 커짐 |
| 서버에 사용자별 git 저장소를 두고 진짜 merge | 줄 단위 3-way merge | 충돌은 파일 단위로 고르면 충분해 merge를 쓸 데가 없는데, 디스크 상태를 가진 서버를 운영해야 함 |
| Automerge, Yjs 같은 CRDT | 동시 편집 자동 병합 | 공동 편집이 아니라 핵심 가치를 쓸 곳이 없고, 마크다운을 CRDT 모델로 옮기는 비용만 남음 |

세 대안 모두 기능 자체는 훌륭하지만, 이 용도에서는 쓰지 않을 기능의 비용을 치르게 됩니다. 특히 서버는 Cloud Run이라 디스크 상태를 갖지 않는 편이 맞았습니다.

---

## 채택: 내용은 해시 주소로, DB에는 포인터 하나만

결정은 두 저장소에 역할을 나누는 것이었습니다.

- 문서 **내용**은 SHA-256 해시를 주소로 삼아 GCS에 불변 객체로 저장합니다.
- Postgres에는 문서(경로)마다 **"지금 가리키는 해시" 하나**만 둡니다.

```
GCS   plans/users/{userId}/objects/{sha256}      내용 (불변, 사용자별)

plan_files        (userId, path) 유일
  hash            현재 해시, NULL이면 지움 표시(tombstone)
  size, owner
  revision        사용자별 단조 증가 순번

plan_sync_states  userId 기본키
  revision        그 사용자의 마지막 revision
```

- **내용 중복이 자동으로 사라집니다.** 같은 내용은 같은 해시라서 한 번만 저장됩니다. 계획 폴더를 `done/`으로 옮겨도 내용이 같으면 새 객체가 생기지 않습니다.
- **평소 경로가 단순합니다.** 대부분의 쓰기는 "객체 저장 + 포인터 갱신"으로 끝납니다.
- **충돌을 예외 경로로 몰 수 있습니다.** 쓰기 요청에 "마지막으로 본 해시"를 함께 보내면, 서버의 포인터와 비교하는 것만으로 충돌을 판정할 수 있습니다. 이 판정은 2편에서 다룹니다.

### 구조에서 따라 나온 세부 결정

- **객체는 사용자별로 따로 저장합니다.** 모든 사용자의 같은 내용을 하나로 합치면 해시만 알면 다른 사람의 내용을 받을 수 있는 경로가 생깁니다. 객체 키를 요청한 사용자의 ID로만 만들고, 중복 제거는 한 사용자 안에서만 일어나게 했습니다.

```ts
// 객체 키를 요청한 사용자로만 만들어서 다른 사용자의 객체에 닿지 않게 한다.
function objectKey(userId: string, hash: string): string {
  return `plans/users/${userId}/objects/${hash}`;
}
```

- **지움은 tombstone으로 남깁니다.** 행을 지우면 다른 기기는 "원래 없던 파일"과 "지워진 파일"을 구분할 수 없습니다. `hash`를 NULL로 만든 행을 남겨 다른 기기가 지움을 받아 가게 했습니다.
- **같은 해시를 여러 경로가 함께 씁니다.** 그래서 객체를 지울 때는 "이 해시를 아직 가리키는 행이 있는가"를 확인해야 하고, 이 확인을 `(userId, hash)` 인덱스가 받칩니다.
- **메타데이터 저장소는 이미 쓰는 Postgres로 정했습니다.** ADR에서는 "Cloud SQL 또는 Firestore"로 열어 두었지만, 포인터 갱신에 행 잠금과 트랜잭션이 필요했고 API 서버가 이미 Supabase Postgres를 쓰고 있었습니다.

## 처음 충돌 설계: 충돌 판본을 서버에 남긴다

첫 ADR(0018)에는 충돌을 이렇게 다루기로 적었습니다.

> `base`가 현재 해시와 다르면 원래 문서는 건드리지 않고, 보낸 내용을 `main-conflict-{기기id}` 같은 별도 객체로 저장한 뒤 충돌로 응답합니다. 사용자가 그때 가서 고릅니다.

git의 충돌 브랜치와 비슷한 발상입니다. 늦게 도착한 쪽의 내용을 서버에 보관해 두면 어느 기기에서든 충돌을 보고 고를 수 있을 것 같았습니다. 같은 ADR의 "결과" 절에는 대가도 적었습니다. 사용자가 충돌 객체를 방치하면 고아 객체로 쌓이므로, 정리 정책(예: N일 후 삭제)이 후속 과제로 남는다는 것입니다.

---

## 구현하면서 보인 것: 충돌을 발견한 기기에는 두 판이 다 있다

앱의 동기화 엔진을 만들면서 충돌이 실제로 어떻게 발견되는지 따라가 봤습니다.

1. 기기 B가 파일을 올립니다. `base`가 서버와 달라 `conflict`를 받습니다.
2. 응답에는 서버의 현재 해시(`current`)가 들어 있습니다. B는 이 해시로 서버 판을 내려받을 수 있습니다.
3. B의 로컬 파일은 B가 올리려던 판 그 자체입니다.

즉 **충돌을 발견하는 기기에는 로컬 판과 서버 판이 이미 모두 있습니다.** 서버에 충돌 판본을 따로 저장하면 그 기기가 이미 가진 내용을 한 번 더 보관하는 셈이고, 그 대가로 충돌 객체의 정리 정책, 충돌 객체를 나열하고 고르는 API가 따라옵니다. "다른 기기에서도 충돌을 고를 수 있다"는 이점은 남지만, 한 사람이 기기를 바꿔 쓰는 용도라 발견한 기기에서 바로 푸는 것으로 충분하다고 판단했습니다.

### 바뀐 설계: 서버는 판정만, 푸는 것은 앱이

새 ADR(0028)에서 충돌 판본을 서버에 저장하지 않기로 했습니다. 이 기기의 파일과 서버 판을 각각 그대로 둔 채 충돌로 표시하고, 충돌을 발견한 기기에서 두 판을 좌우로 나란히 비교해 한쪽을 고릅니다(`@codemirror/merge`의 `MergeView`). 충돌 난 파일은 풀릴 때까지 자동 동기화에서 뺍니다.

앱은 로컬, 기준, 서버 세 해시로 다음 동작을 정합니다. 위에서부터 먼저 맞는 줄을 따릅니다.

| 조건 | 의미 | 동작 |
| ---- | ---- | ---- |
| 로컬 = 서버, 기준도 같음 | 바뀐 것 없음 | 없음 |
| 로컬 = 서버, 기준은 다름 | 양쪽이 같은 내용으로 바뀜 | 기준만 맞춤 |
| 로컬 = 기준 | 서버만 바뀜 | 내려받기 (서버가 지웠으면 로컬도 지움) |
| 서버 = 기준 | 로컬만 바뀜 | 올리기 (로컬이 지웠으면 서버도 지움) |
| 위에 모두 해당 없음 | 양쪽이 서로 다르게 바뀜 | 충돌 |

### 함께 정한 것들

충돌 처리를 앱으로 옮기면서, 0018이 미뤄 둔 "언제, 무엇을, 어떤 단위로" 동기화할지도 0028에서 정했습니다.

- **기준 해시는 계정마다 따로 둡니다.** 기기마다 하나만 두면, 한 기기에서 계정을 바꿨을 때 다른 계정의 기준으로 판정해 엉뚱한 덮어쓰기가 생깁니다.
- **처음 켤 때는 기준 없이 올립니다.** 서버가 같은 내용이면 기준만 맞추고, 다른 내용이면 충돌로 판정합니다. 이미 계획이 있는 두 기기에서 처음 켜면 충돌이 한꺼번에 날 수 있다는 점은 받아들였습니다.
- **사람이 누르는 저장 버튼은 두지 않았습니다.** 쓰기의 대부분을 에이전트가 하므로, 사람이 누르기를 기다리면 다른 기기가 옛 계획으로 작업을 시작합니다. 2초 동안 더 바뀌지 않은 파일을 묶어 올리고, 30초마다 다시 훑습니다.
- **앱은 GCS에 직접 접근하지 않습니다.** 서명된 URL로 직접 올리면 요청 수는 줄지만 쓰기 판정과 객체 쓰기가 갈라집니다. 2편에서 다룰 순서 규칙이 서버 한 곳에서만 성립하도록 모든 내용은 API를 거칩니다.

## 결정의 일부만 뒤집을 때 ADR을 다루는 방식

Belloga의 ADR 규칙은 "기존 결정을 뒤집으면 새 문서를 만들고, 옛 문서는 지우지 않는다"입니다. 이번에는 저장 방식은 그대로이고 충돌 처리만 바뀌었습니다. 그래서 0018의 상태를 `대체됨`이 아니라 `일부 대체됨 (→ 0028)`으로 바꾸고, 결과 절 끝에 날짜를 붙여 구현 때 바뀐 점을 적었습니다.

```
- 상태: 일부 대체됨 (→ 0028)

## 결과
- 사용자가 충돌 객체를 방치하면 고아 객체로 쌓입니다. 정리 정책은 후속 과제로 남깁니다.
- (2026-10-20 구현) 충돌 판본은 서버에 저장하지 않습니다. 충돌을 발견한 기기에 두 판이
  모두 있으므로 그 기기에서 비교해 고릅니다. 그래서 위의 충돌 객체와 그 정리 정책은 없어집니다.
```

옛 문장을 고쳐 쓰지 않고 남겨 둔 이유는, 나중에 "왜 충돌 판본을 서버에 안 두지?"라는 질문이 다시 나올 때 한 번 검토하고 버린 안이라는 기록이 필요하기 때문입니다. 0028의 "검토한 대안"에도 같은 안을 기각 사유와 함께 올렸습니다.

---

## 이 설계로 받아들인 것

- **충돌은 파일 단위입니다.** 한 문서 안에서 양쪽이 서로 다른 곳을 고쳤어도 한쪽 판을 통째로 골라야 합니다.
- **이력은 남지 않습니다.** 참조가 사라진 객체는 지우므로 버전 기록으로 쓸 수 없습니다. 파일 이력 보관은 후속 과제입니다.
- **다른 기기의 변경은 최대 30초 늦게 옵니다.** 앱이 꺼져 있는 동안에는 받지 않습니다.

---

## 정리

- 저장 방식을 고르기 전에 "공동 편집이 아니고, 충돌은 드물지만 생기면 잃으면 안 된다"는 제약을 먼저 적었고, 그 제약에서 CRDT와 서버 git을 기각했습니다.
- 내용은 해시 주소의 불변 객체로, DB에는 문서당 포인터 하나만 두어 평소 경로를 단순하게 만들고 충돌을 예외 경로로 몰았습니다.
- 충돌 판본을 서버에 남기려던 설계는, 충돌을 발견한 기기에 두 판이 이미 있다는 점을 알고 철회했습니다. 옛 ADR은 지우지 않고 `일부 대체됨`으로 남겼습니다.
