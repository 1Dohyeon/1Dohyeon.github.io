# Belloga 검색 (2) pgvector와 pg_trgm을 RRF로 합친 하이브리드 검색, 그리고 MCP 대신 CLI

[1편](/blog/2026-11-03-belloga-search-1-indexing)에서 완료한 계획을 청크로 나눠 임베딩해 두었습니다. 이번 글은 그 청크를 찾는 검색과, 찾은 결과를 에이전트 세션에 어떤 형태로 건넸는지를 다룹니다.

---

## 왜 벡터만으로는 부족한가

벡터 검색은 "결제 재시도 설계"로 검색해서 "PG 응답 지연 시 재처리" 문서를 찾는 데 강합니다. 표현이 달라도 뜻이 가까우면 찾아냅니다. 반대로 `judgeWrite`, `ifGenerationMatch`처럼 정확한 식별자로 찾을 때는 약합니다. 임베딩은 뜻을 압축하므로, 드문 식별자가 들어 있다는 사실이 벡터에 잘 남지 않습니다.

계획 문서에는 두 종류의 검색이 다 필요합니다. 그래서 벡터 검색과 키워드 검색을 따로 돌린 뒤 합치기로 했습니다.

---

## 두 검색

### 벡터: pgvector 코사인 거리

```sql
SELECT ..., 1 - (c.embedding <=> $vector) AS score
FROM plan_chunks c
WHERE <사용자, 소유자, 문서 종류 범위> AND c.model = $model
ORDER BY c.embedding <=> $vector
LIMIT 200
```

- 지금 모델로 만든 벡터끼리만 비교합니다. 모델이 다른 벡터는 같은 공간에 있지 않습니다.
- 지운 파일의 청크는 색인 정리 전이라도 `plan_files`를 확인해 뺍니다.

### 키워드: ILIKE로 거르고 word_similarity로 정렬

```sql
SELECT ..., word_similarity($query, c.content) AS score
FROM plan_chunks c
WHERE <범위> AND c.content ILIKE '%' || $escaped || '%' ESCAPE '\'
ORDER BY word_similarity($query, c.content) DESC, c.id
LIMIT 200
```

- 대소문자를 무시한 부분 일치로 먼저 거르고, `pg_trgm`의 `word_similarity`로 순서를 매깁니다. 임계값으로 거르지 않으므로, 포함만 되어 있으면 결과에 나옵니다.
- 검색어의 `%`, `_`는 이스케이프합니다. 사용자가 친 `_`가 와일드카드가 되면 엉뚱한 결과가 나옵니다.

### 벡터 인덱스는 두지 않았다

HNSW나 IVFFlat 같은 근사 인덱스는 두지 않았습니다. 검색은 항상 한 사용자, 켠 소유자의 청크로 좁혀서 하고, 그 양이 작아서 정확 검색(전체 비교)으로 충분합니다. 근사 인덱스는 결과를 조금 놓칠 수 있는데, 그 대가를 치를 만큼의 양이 아닙니다. 데이터가 커지면 그때 다시 봅니다.

---

## 두 결과를 합치기: 점수가 아니라 순위로

벡터 점수는 코사인 유사도(0~1 근처)이고, 키워드 점수는 `word_similarity`입니다. 척도가 달라서 그대로 더하면 한쪽이 결과를 지배합니다. 정규화를 하려 해도, 쿼리마다 점수 분포가 달라 어디에 맞출지 정하기 어렵습니다.

그래서 점수는 버리고 **순위만 쓰는 RRF(Reciprocal Rank Fusion)**로 합쳤습니다. 각 목록에서 r번째에 나온 청크는 `1 / (k + r)`을 받고, 두 목록에 모두 나오면 더합니다. k는 관례적인 값 60을 썼습니다.

```ts
// 청크 id로 합치고 점수를 1/(k+순위)의 합으로 바꾼다. 점수 내림차순, 동점이면 id 오름차순이다.
export function fuseRrf(lists: ChunkHit[][], k = 60): ChunkHit[] {
  const fused = new Map<string, ChunkHit>();
  for (const list of lists) {
    list.forEach((hit, index) => {
      const add = 1 / (k + index + 1);
      const found = fused.get(hit.id);
      if (found) found.score += add;
      else fused.set(hit.id, { ...hit, score: add });
    });
  }
  return [...fused.values()].sort((a, b) => b.score - a.score || compareText(a.id, b.id));
}
```

- 두 검색에서 모두 상위에 오른 청크가 가장 위로 올라갑니다.
- 한쪽에서만 1등인 청크도 `1/61`을 받아 상위권에 남습니다. 식별자 검색처럼 키워드에서만 잡히는 결과가 묻히지 않습니다.
- 동점은 id로 정렬해서 같은 검색어에 결과 순서가 늘 같습니다. 테스트하기도 쉽습니다.

### 청크를 계획 단위로 묶는다

사용자가 찾는 것은 청크가 아니라 계획입니다. 청크를 계획(소유자/저장소/브랜치)으로 묶고, 계획의 점수는 가장 높은 청크의 점수로 둡니다. 계획마다 근거 청크를 최대 3개까지 보여 줍니다. 모드마다 200개씩 넉넉히 가져오는 이유도 여기 있습니다. 한 계획의 청크가 상위를 채우면 다른 계획이 밀려나기 때문입니다.

### 임베딩이 실패하면 몰래 대신하지 않는다

질의 임베딩이 실패하면 키워드 결과만으로 조용히 대신하지 않고 오류로 알립니다. 사용자는 하이브리드 결과라고 믿고 보는데 실제로는 키워드 결과라면, 결과가 이상할 때 원인을 찾을 수 없습니다. 서버에 검색 설정이 없을 때도 마찬가지로 안내만 보여 줍니다.

## 세션에 검색을 건네는 방법: MCP 대신 CLI

검색을 만든 진짜 목적은 사람보다 에이전트였습니다. Belloga 터미널에서 켠 Claude Code 세션이 새 작업을 설계하기 전에, 비슷한 완료 계획을 직접 찾아 읽게 하고 싶었습니다. 답변은 세션의 Claude가 만들고, 서버는 검색만 합니다(1편의 금지 목록).

| 대안 | 판단 |
| ---- | ---- |
| MCP 서버 등록(`claude mcp add -s user`) | 도구 목록에 바로 보여 편하지만, user 범위라 Belloga 밖의 세션에도 들어갑니다. "Belloga 안에서만 적용한다"는 원칙과 부딪히고, 앱이 처음으로 `~/.claude.json`을 고치게 되어 기각 |
| 프롬프트마다 검색 결과 넣기(UserPromptSubmit 훅) | 부르지 않아도 되지만 프롬프트마다 지연, 컨텍스트 토큰, 질의 임베딩 비용이 들고 대부분은 잡음이라 기각 |
| 스크립트가 서버를 직접 호출 | 앱 없이도 되지만, 세션 토큰을 파일이나 환경 변수로 터미널에 내보내야 해서 기각 |
| **CLI 스크립트 + 앱 프록시 (채택)** | 세션 시작 안내에 사용법 한 단락만 붙이고, 세션 토큰은 앱 main 프로세스 안에 둠 |

여기서 세션 토큰은 Belloga 세션 토큰입니다. 앱에서 GitHub로 로그인하면 Belloga API 서버가 발급하는 인증 토큰이고, 동기화, 색인, 검색 요청은 모두 이 토큰으로 인증합니다. 앱에서는 Electron의 main 프로세스가 이 토큰을 암호화해 보관하고, 화면(renderer)이나 터미널로는 넘기지 않습니다. 스크립트가 서버를 직접 부르게 하려면 이 토큰을 터미널로 내보내야 하고, 그러면 세션 안의 에이전트나 다른 프로세스가 읽을 수 있습니다.

채택한 구조는 이렇습니다.

1. 앱이 훅 스크립트 폴더에 `belloga-plans.mjs`를 쓰고, 세션 시작 안내 끝에 `search`, `read` 두 명령의 사용법을 붙입니다. "참고할 수 있다"는 강제하지 않는 문장입니다.
2. 스크립트는 서버를 직접 부르지 않고, 앱의 로컬 훅 서버(`127.0.0.1`)에 요청합니다. 접속에 쓰는 포트와 접속 토큰(`BELLOGA_HOOK_PORT`, `BELLOGA_HOOK_TOKEN`)은 앱이 터미널을 열 때 환경 변수로 넣습니다. 이 접속 토큰은 로컬 훅 서버에만 쓰이고, 서버 API는 부를 수 없습니다.
3. 앱 main 프로세스가 로그인한 계정의 Belloga 세션 토큰을 붙여 API를 대신 부릅니다. 세션 토큰은 main 밖으로 나가지 않습니다.
4. 검색은 계획 최대 10개, 읽기는 50,000자까지만 텍스트로 출력합니다.

### 실패를 실패로 보이지 않게 한 이유

Belloga 밖에서 스크립트를 실행하거나, 앱이 꺼져 있거나, 로그아웃 상태면 안내 문장을 출력하고 **종료 코드 0**으로 끝냅니다. 오류로 끝내면 원인은 분명히 드러나지만, Claude가 실패로 보고 재시도를 반복하거나 사용자에게 고치라고 권합니다. 사용할 수 없는 상황은 "고칠 오류"가 아니라 "지금은 쓸 수 없음"이라서, 정상 종료로 알리는 편을 골랐습니다.

### 사용자 설정은 최소한만, 되돌릴 수 있게

검색할 때마다 권한 확인 창이 뜨면 세션이 스스로 참고한다는 목적과 어긋납니다. 그래서 `~/.claude/settings.json`의 `permissions.allow`에 이 스크립트 실행 규칙 하나만 더합니다. 앱이 더한 규칙은 기록해 두고 끌 때 그것만 뺍니다. 사용자가 먼저 같은 규칙을 넣어 두었다면 기록하지 않으므로, 끌 때도 사용자의 규칙은 남습니다.

---

## 정리

- 벡터는 뜻으로, 키워드는 식별자로 찾는 데 강해서 둘을 따로 돌리고, 척도가 다른 점수 대신 순위만 쓰는 RRF로 합쳤습니다.
- 검색 범위가 한 사용자로 좁고 작아서 근사 벡터 인덱스 없이 정확 검색을 쓰고, 임베딩 실패는 키워드로 몰래 대신하지 않습니다.
- 에이전트에게는 MCP 대신 CLI 스크립트를 주고, API 호출은 앱이 대신해 Belloga 세션 토큰을 main 밖으로 내지 않았습니다.
