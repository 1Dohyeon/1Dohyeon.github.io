# Belloga 모듈 경계: 평평한 45개 파일을 층 표와 eslint로 나누기

Belloga 데스크톱 앱(Electron)의 코드가 늘면서 어느 파일이 어느 책임에 속하는지, 무엇이 무엇에 기대는지 찾기 어려워졌습니다. 이 글은 프로세스 안쪽을 도메인 폴더로 나누고, 폴더 사이의 의존 방향을 lint로 강제한 결정 기록(ADR)을 정리합니다.

---

## 쌓인 불편 세 가지

- **의존 방향을 찾기 어렵습니다.** 모듈이 폴더가 아니라 파일 이름 접두어(`plan*`, `claude*`, `git*`)로만 구분되고, 방향을 강제하는 장치가 없었습니다.
- **`src/main/`에 파일 45개가 평평하게 놓여 있었습니다.** 어느 파일이 어느 책임인지 이름으로만 짐작해야 했습니다.
- **무엇이든 들어갈 수 있는 폴더가 있었습니다.** renderer의 `App.tsx`는 1,075줄이었고, `common/`, `hooks/`처럼 이름이 책임을 말해 주지 않는 폴더가 있었습니다.

방향이 거꾸로 된 의존도 두 가지 있었습니다. 앱 메뉴 파일이 언어 상태와 메뉴 IPC 등록까지 맡아서, 메뉴와 무관한 모듈이 언어를 얻으려고 메뉴에 의존했습니다. 또 Claude 설정 모듈이 계획(plan) 훅 스크립트를 가져다 설치해서, Claude 모듈이 계획 경로와 스크립트 이름을 알고 있었습니다.

---

## 결정: 도메인 폴더와 층 표

**main, renderer 각 프로세스의 안쪽을 도메인 폴더로 나누고, 폴더 사이에 허용하는 의존 방향을 표로 정해 eslint `no-restricted-imports`로 검사합니다.** 프로세스 경계(`main / preload / renderer / shared`)는 그대로 둡니다.

main은 이렇게 나눴습니다. 아래 층은 위 층을 import하지 않고, 같은 층끼리는 표에 적힌 것만 import합니다.

| 층 | 모듈 | import해도 되는 모듈 |
| --- | ---- | ---- |
| 0 | `persistence`, `backend` | (없음) |
| 1 | `i18n` | `persistence` |
| 1 | `account` | `persistence`, `backend` |
| 2 | `window` | `i18n`, `persistence` |
| 2 | `git`, `notifications`, `claude` | (없음) |
| 3 | `connections` | `git`, `persistence` |
| 3 | `terminal` | `claude` |
| 4 | `files` | `connections`, `git`, `i18n` |
| 5 | `plan` | `files`, `git`, `i18n`, `persistence`, `claude` |
| 6 | `sync` | `account`, `backend`, `persistence`, `plan` |
| 7 | `archive` | `account`, `backend`, `persistence`, `sync` |
| 8 | `ipc` | 전부 |

- **여러 도메인을 잇는 조율은 `ipc/`가 맡습니다.** 예를 들어 worktree를 만들 때 계획 폴더를 심고, 지울 때 셸을 먼저 끄는 일입니다. 도메인끼리 서로를 부르지 않고 맨 위의 조립 층이 묶습니다.
- **IPC 채널 등록은 `ipc/`에만 둡니다.** 도메인 폴더는 `ipcMain`을 모릅니다.
- **거꾸로 된 의존 두 개를 바로잡았습니다.** 언어 상태는 `i18n/`으로 옮기고 메뉴는 메뉴를 만드는 일만 합니다. 계획 훅에 관한 것은 모두 `plan/`으로 옮겨 방향을 `plan → claude`로 바꿨습니다. Claude 모듈은 이제 설정 파일 접근과 세션 상태 훅만 압니다.

renderer도 같은 방식으로 `ui/`, `lib/`(도메인을 모르는 부품과 도구) → `features/*` → `workspace/` → `app-shell/` → `App.tsx` 순서의 층으로 나눴습니다. 같은 층의 feature끼리는 서로 import하지 않습니다.

### 프로세스 경계 규칙

| 대상 | 금지 | 이유 |
| ---- | ---- | ---- |
| `src/renderer/**` | `electron`, `node:*` | renderer는 preload가 넘겨준 API로만 main과 이야기합니다 |
| `src/shared/**` | `electron`, `node:*`, main, renderer, preload | shared는 세 프로세스가 모두 쓰므로 어느 쪽에도 기대지 않습니다 |

## 참고 사례에서 가져온 것과 가져오지 않은 것

참고 사례로 오픈소스 Orca를 조사했습니다. Orca는 TS 코드가 Belloga의 약 110배라서, 규모 때문에 생긴 장치는 빼고 작은 앱에서도 효과가 있는 관례만 가져왔습니다.

| Orca 관례 | 적용 |
| ---- | ---- |
| main을 도메인 폴더로 나눔 | 채택 |
| 도메인 폴더는 `ipcMain`을 모르고 `ipc/`가 등록만 함 | 채택 |
| `common`, `utils`, `helpers`, `misc` 같은 폴더 이름 금지 | 채택 |
| barrel(`index.ts`)을 거의 쓰지 않음 | 채택. 파일을 직접 import해야 의존이 보입니다 |
| 경계 검사 테스트(약 100개) | 방식만 바꿔 채택. 테스트 대신 이미 쓰는 eslint로 검사합니다 |
| 파일 길이 lint | 가져오지 않음. 긴 파일은 리뷰에서 봅니다 |
| 큰 도메인을 하위 폴더로 나눔 | 가져오지 않음. Belloga 도메인은 가장 큰 것도 파일 5~6개입니다 |
| preload 분할, 단일 store, 채널 이름 일치 테스트 | 가져오지 않음. 규모에 비해 비용이 큽니다 |

그 밖에 검토한 대안도 있었습니다.

- **역할별 구조를 두고 큰 파일만 쪼개기**: 변경은 가장 작지만, 접두어로만 모듈을 구분하는 상태가 그대로라 의존 방향을 찾기 어렵다는 불편이 남습니다.
- **`eslint-plugin-import`의 `no-cycle`로 순환 잡기**: 파일 단위 순환까지 잡지만 새 의존성을 들여야 합니다. 층 표를 지키면 모듈 단위 순환은 구조적으로 생기지 않으므로 기각했습니다.

## 결정의 결과로 적어 둔 것

- **새 모듈 폴더를 만들면 ADR의 층 표와 eslint 설정의 모듈 표를 함께 고쳐야 합니다.** 표가 두 곳에 있는 셈입니다.
- **flat config에서는 한 파일에 같은 규칙을 거는 블록이 여럿이면 마지막 블록의 옵션만 남습니다.** 그래서 모듈 방향 금지, `ipcMain` 금지, 프로세스 경계 금지를 파일마다 한 블록에 합쳐 만듭니다.
- **규칙은 import 문자열의 폴더 이름으로 판단합니다.** 같은 폴더 안의 `./x` import는 검사하지 않으므로, 폴더 안의 파일 단위 순환은 리뷰에서 확인합니다.

이 층 표는 이후 기능을 더할 때도 배치를 정해 주었습니다. 나중에 검색 색인을 동기화 주기 끝에 부르게 했을 때, `sync`가 `archive`를 import하지 않도록 `sync`가 주기 끝 알림을 내보내고 `archive`가 구독하는 구조로 만든 것도 이 표 때문이었습니다.

---

## 정리

- 파일 이름 접두어로만 나뉘던 모듈을 도메인 폴더로 옮기고, 허용하는 의존 방향을 층 표로 정했습니다.
- 표는 문서로만 두지 않고 eslint `no-restricted-imports`로 검사해, 어기면 lint가 실패하게 했습니다.
- 큰 프로젝트의 관례는 "작은 앱에서도 효과가 있는가"를 기준으로 골라 가져왔습니다.
