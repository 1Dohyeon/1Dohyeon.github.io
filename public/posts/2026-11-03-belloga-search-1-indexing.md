# Belloga 검색 (1) 응답 뒤 CPU가 없는 Cloud Run에서 색인하기: 앱이 부르는 pull 방식

[동기화](/blog/2026-10-21-belloga-sync-1-design)로 서버에 완료한 계획이 모이자, "예전에 비슷한 작업을 어떻게 설계했지?"를 기기와 상관없이 찾을 수 있게 되었습니다. 제목이 아니라 요구사항과 설계 내용으로 찾으려면 문서를 나누고 임베딩해 두어야 합니다. 이 글은 그 색인을 언제, 어디서 할지 정한 결정 기록(ADR)을 정리합니다. 검색 자체는 [2편](/blog/2026-11-03-belloga-search-2-hybrid)에서 다룹니다.

---

## 풀어야 할 제약 세 가지

- **"서버는 인가와 저장만 한다"는 원칙이 있었습니다.** 동기화를 설계할 때 판단 로직은 앱에 두기로 했습니다. 임베딩을 서버에서 하려면 이 원칙에 예외를 두어야 합니다.
- **서버는 Cloud Run입니다.** Cloud Run은 요청을 처리하는 동안에만 CPU를 보장하고, 응답을 보낸 뒤에는 CPU가 크게 줄어듭니다. 응답 뒤 백그라운드 작업은 끝까지 돈다고 믿을 수 없습니다.
- **계획 문서에는 회사 코드의 설계가 들어갈 수 있습니다.** 외부 서비스로 무엇을 보낼지는 사용자가 정해야 합니다.

---

## 색인은 언제 하나: 검토한 대안

| 대안 | 판단 |
| ---- | ---- |
| 계획을 올리는 쓰기 요청 안에서 색인 | 쓰기는 사용자 잠금 안에서 돕니다. 잠금 시간에 외부 API 지연이 더해지고, 커밋 뒤 응답 전에 하면 묶음 응답이 앱의 10초 타임아웃에 가까워져서 기각 |
| 응답을 먼저 보내고 백그라운드로 색인 | Cloud Run이 응답 뒤 CPU를 보장하지 않아 기각 |
| 앱에 따로 타이머를 두고 색인 요청 | 이번 주기에 올린 파일이 있었는지 알 수 없어 "올린 게 없으면 부르지 않는다"를 지킬 수 없어서 기각 |
| **앱이 동기화 주기 끝에 색인 요청 (채택)** | 요청 안에서 처리하므로 CPU가 보장되고, 올린 파일이 있을 때만 부를 수 있음 |

Cloud Run에서 믿을 수 있는 실행 시간은 "요청을 처리하는 동안"뿐입니다. 그래서 서버가 스스로 일을 찾아 하는 push 대신, **앱이 요청을 보내 서버가 그 요청 안에서 조금씩 일하는 pull** 구조를 골랐습니다. 앱이 이미 30초 주기로 서버와 통신하므로, 그 주기에 얹으면 새로 운영할 것이 생기지 않습니다.

---

## pull 색인의 동작

1. 앱의 동기화 엔진이 30초 주기 스캔을 마치면 `POST /plans/index/sync`를 부릅니다.
2. 서버는 아직 색인하지 않은 파일을 **한 요청에 최대 10개만** 처리하고, 남은 개수(`remaining`)를 돌려줍니다.
3. `remaining`이 0보다 크면 앱은 다음 주기에도 부르고, 0이면 다음 업로드가 있을 때까지 부르지 않습니다.

```ts
// 앱의 요청 시간 안에 끝내기 위한 한 요청의 파일 수 상한이다.
export const INDEX_SYNC_MAX_FILES = 10;
```

한 번에 다 하지 않고 10개씩 끊는 이유는, 요청 하나가 앱의 타임아웃과 Cloud Run의 요청 시간 안에 확실히 끝나야 하기 때문입니다. 밀린 일은 다음 주기가 이어받습니다.

앱 쪽에서도 의존 방향을 지켰습니다. 동기화 모듈(`sync`)은 색인 모듈(`archive`)을 모르고, `sync`가 "주기 끝" 알림을 내보내면 `archive`가 구독해서 색인을 부릅니다.

### 같은 사용자의 색인이 겹치지 않게: 리스 테이블

두 기기가 같은 순간에 색인을 부르면 같은 파일을 두 번 임베딩하게 됩니다. 동기화 쓰기처럼 트랜잭션 잠금을 오래 쥘 수는 없습니다. 색인은 외부 API를 여러 번 부르는 긴 작업이라 그동안 커넥션을 붙잡게 되기 때문입니다. 그래서 기한이 있는 리스를 행 하나로 표현했습니다.

```sql
INSERT INTO plan_index_leases ("userId", "leaseUntil")
VALUES ($1, now() + interval '60 seconds')
ON CONFLICT ("userId") DO UPDATE SET "leaseUntil" = EXCLUDED."leaseUntil"
WHERE plan_index_leases."leaseUntil" < now();
```

- 행이 없거나 기한이 지났으면 영향받은 행이 1이고, 리스를 얻은 것입니다.
- 다른 요청이 리스를 쥐고 있으면 `WHERE`에 걸려 0이고, `409 index_busy`로 응답합니다.
- 끝나면 리스를 지웁니다. 서버가 처리 중에 죽거나 해제가 실패해도 60초가 지나면 저절로 다시 잡을 수 있습니다.
- 실제 코드는 열에 시간대가 없어서 `now()`를 UTC로 바꿔 비교합니다.

### 실패해도 끝낸 만큼은 남긴다

파일마다 따로 커밋합니다. 10개 중 7번째에서 임베딩 API가 실패해도 앞의 6개는 색인된 채로 남고, 나머지는 다음 주기에 다시 처리됩니다.

```ts
// 파일마다 따로 커밋하므로 중간에 실패해도 그 전에 끝낸 파일의 색인은 남는다.
async sync(userId: string): Promise<SyncResult> {
  if (!(await this.store.tryLease(userId))) {
    throw new ConflictException({ status: 'index_busy' });
  }
  try {
    const stale = await this.store.listStale(userId);
    await this.store.removePaths(userId, stale);
    const pending = await this.store.listPending(userId, INDEX_SYNC_MAX_FILES);
    for (const file of pending) { /* 파일마다 색인하고 커밋 */ }
    return { indexed, removed: stale.length, skipped, remaining: await this.store.countPending(userId) };
  } finally {
    await this.release(userId);
  }
}
```

지워진 파일이나 색인 스위치가 꺼진 소유자의 색인 데이터(`stale`)도 같은 요청에서 먼저 정리합니다.

## 청크와 임베딩: 바뀐 부분만 다시

- 문서는 `##` 제목 단위로 나누고, 한 청크는 최대 1,500자입니다. 코드 펜스 안의 `##`는 제목으로 보지 않고, 긴 단락은 줄 단위, 그래도 긴 줄은 글자 수로 자릅니다.
- 임베딩 입력은 "소유자/저장소/브랜치, 문서 종류, 제목, 본문"을 이은 문자열이고, 그 SHA-256을 `chunkHash`로 둡니다.
- 같은 `(chunkHash, model)`의 벡터가 이미 있으면 다시 쓰고, 없는 것만 임베딩합니다. 문서 일부만 고쳐도 바뀐 청크만 비용이 듭니다.
- 벡터에 모델 이름을 함께 저장하므로, 임베딩 모델을 바꾸면 옛 모델의 벡터는 재사용되지 않아 다시 색인할 대상이 저절로 정해집니다.

```ts
// 벡터는 임베딩 입력으로 정해지므로, 같은 벡터를 다시 쓸 수 있는지는 이 해시로 가른다.
export function embeddingHash(meta: PlanMeta, chunk: PlanChunkDraft): string {
  return createHash('sha256').update(embeddingInput(meta, chunk)).digest('hex');
}
```

## "서버는 저장만" 원칙의 예외를 좁게 적었다

임베딩을 앱에서 하면 원칙은 지킬 수 있습니다. 하지만 앱에 모델을 싣거나 기기마다 외부 키를 두어야 하고, 기기마다 모델 버전이 달라지면 벡터끼리 비교할 수 없습니다. 그래서 서버에 예외를 두되, ADR에 허용과 금지를 함께 적었습니다.

- **허용**: 색인 스위치를 켠 소유자의 완료 계획을 나누고 임베딩해 저장하는 것, 그 청크를 검색해 돌려주는 것
- **계속 금지**: 동기화 쓰기 판정을 바꾸는 것, 무엇을 언제 색인할지 서버가 정하는 것, 서버가 LLM으로 답변이나 요약을 만드는 것

pull 방식은 이 금지 목록과도 맞습니다. 언제 색인할지는 앱이 부르는 시점이 정하고, 서버는 받은 요청 안에서만 일합니다.

임베딩 업체는 Vertex AI로 정했습니다. OpenAI나 Voyage를 쓰면 문서가 새 업체로 넘어가지만, Vertex AI는 서버가 이미 쓰는 Google Cloud 안이라 데이터가 그 밖으로 나가지 않습니다.

## 외부 전송은 사용자가 켠다

- 색인 스위치는 소유자(GitHub 사용자 또는 조직)마다 켜고, 기본값은 꺼짐입니다. 회사 조직의 계획은 끄고 개인 계정만 켤 수 있습니다.
- 스위치 값은 서버에 계정 단위로 둡니다. 색인 대상을 서버가 골라야 하고, 한 소유자의 문서는 어느 기기가 올렸든 같은 서버 데이터라 기기별 스위치는 뜻이 없기 때문입니다.
- 켤 때 "Vertex AI로 전송되고 모든 기기에 적용된다"는 확인 창을 거칩니다. 끄면 서버가 그 소유자의 검색 데이터를 바로 지웁니다.
- 외부 전송을 켜는 스위치라 화면에서 낙관적으로 바꾸지 않고, 서버가 받아들인 값만 보여 줍니다.

---

## 받아들인 것

- 완료한 계획이 검색에 나오기까지 몇십 초에서 몇 분이 걸립니다. 앱이 꺼져 있으면 색인하지 않습니다.
- 청크 길이(1,500자)와 임베딩 모델은 평가 전의 임시 값입니다. 바뀌면 서버가 다시 색인합니다.

---

## 정리

- Cloud Run에서 믿을 수 있는 실행 시간은 요청 처리 중뿐이라, 앱이 동기화 주기 끝에 부르고 서버가 그 요청 안에서 10개씩 처리하는 pull 방식으로 색인했습니다.
- 겹치는 색인은 기한 있는 리스 행으로 막고, 파일마다 커밋해 중간 실패에도 끝낸 만큼은 남겼습니다.
- 임베딩을 서버에서 하려고 "저장만" 원칙에 예외를 두되, 허용과 금지를 ADR에 함께 적어 범위를 좁혔습니다.
